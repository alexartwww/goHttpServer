Все знания здесь из открытых источников: RFC 9110 (семантика HTTP) и RFC 9112 (HTTP/1.1), документация nginx, исходники стандартной библиотеки Go (`net/http`, `net`, `os`). Ссылки на разделы RFC стоят прямо в тексте — их стоит открыть и прочитать.

## 1. Модуль Go

**Файлы:** `go.mod` (новый), импорты в `main.go`.

**Что было:** проект собирался в старом режиме GOPATH, импорты вида `alexartwww/goHttpServer/http`.

**Что сделано:**
- `go.mod` с `module github.com/alexartwww/goHttpServer` и `go 1.25.5`.
- Импорты переведены на полный путь модуля.

**Зачем:** без модуля не работают fuzz-тесты (`go test -fuzz`), зависимости не фиксируются, `go install` по ссылке на GitHub невозможен.

**Мелочь:** в `go.mod` указана версия 1.25.5, а локально стоял Go 1.25.4. Go сам скачал нужный toolchain (механизм `GOTOOLCHAIN=auto`, появился в Go 1.21). Это видно по `go version` внутри проекта.

Потом структура была переделана вручную: `cmd/`, `internal/http`, `internal/file`, `pkg/config`. `internal/` — стандартное соглашение Go: такие пакеты нельзя импортировать из других модулей.

## 2. Парсер запроса на конечном автомате

**Файлы:** `internal/http/parser.go` (новый), `internal/http/parser_test.go` (новый). Удалены `http/requestParser.go` и `http/param.go`.

### Что было не так в старом парсере

1. **Не автомат, а 13 булевых флагов** (`flagMethod`, `flagIri`, …). Флаги независимы, поэтому возможны бессмысленные комбинации (одновременно «читаем метод» и «читаем значение заголовка»). Проверить все переходы невозможно.
2. **Склейка строк на каждый байт:** `request.Method = request.Method + string(v)`. Строки в Go неизменяемы, каждая склейка — новая аллокация и копирование всего, что было. Для строки длины n это O(n²). Итог: 866 аллокаций и ~40 КБ памяти на один запрос Chrome.
3. **Нет проверок:** любые байты принимаются, нет лимитов на размер.

### Как устроен новый

**Состояния** — явный тип `type state uint8` и 16 констант:

```
stMethod -> stTargetStart -> stPath -> (stQuery) -> stVersion ("HTTP/")
-> stVersionMajor -> stVersionDot -> stVersionMinor -> stRequestLineEnd -> (stRequestLineLF)
-> stHeaderStart <-> stHeaderName -> stHeaderValueOWS -> stHeaderValue -> (stHeaderLF)
-> ... -> stHeadEndLF -> stDone
```

Цикл по байтам, на каждом байте `switch p.state`. В каждый момент автомат ровно в одном состоянии — невозможных комбинаций нет.

**Ключевые идеи:**

1. **Возобновляемость.** `Feed(buf)` запоминает позицию `pos` и состояние. Если байты кончились посреди запроса — возвращает `false, nil`. Следующий вызов с тем же буфером плюс новые байты продолжает с того же места. Это и есть главное преимущество автомата: TCP отдаёт данные кусками произвольного размера, и не нужно ждать «полного» запроса или разбирать его заново.
2. **Смещения вместо строк.** Результат — пары `span{start, end}` внутри буфера вызывающего. `Method()`, `Path()`, `Header()` возвращают срезы (`buf[start:end]`) — это не копия, а «окно» в тот же массив. Отсюда **0 аллокаций**.
3. **Фиксированный массив заголовков:** `headers [MaxHeaders]field` лежит прямо в структуре `Parser`, а не в слайсе, который рос бы через `append`.
4. **Таблицы классов байтов:** `tokenTable [256]bool`, `fieldTable [256]bool` заполняются в `init()`. Проверка «допустимый ли символ» — одно обращение к массиву вместо цепочки сравнений.
5. **Сравнение без аллокаций:** `equalFold(b []byte, s string)` сравнивает ASCII без учёта регистра, не превращая `[]byte` в `string`.

**Строгость по RFC (что отклоняется):**

| Случай | Ответ | Источник |
|---|---|---|
| недопустимый символ в методе или имени заголовка (не `tchar`) | 400 | RFC 9110, 5.6.2 |
| пробел перед двоеточием `Host : x` | 400 | RFC 9112, 5.1 |
| строка заголовка начинается с пробела (obs-fold, «перенос») | 400 | RFC 9112, 5.2 |
| управляющие символы в значении | 400 | RFC 9110, 5.5 |
| target не начинается с `/` или `*` (абсолютная форма `http://…`) | 400 | сервер не прокси |
| версия не 1.0/1.1 | 505 | |
| заголовки длиннее 8 КБ или больше 64 полей | 431 | RFC 6585 |
| URI не влез в 8 КБ | 414 | |

**Что принимается (тоже по RFC):**
- голый `\n` вместо `\r\n` (RFC 9112, 2.2: «MAY recognize a single LF»);
- пустые строки перед строкой запроса (там же);
- пробелы вокруг значения заголовка обрезаются: начальные пропускаются состоянием `stHeaderValueOWS`, конечные отсекаются через `valueEnd` — позицию последнего не-пробельного байта.

**Ошибки** — тип `*Error{Status, Reason}` и готовые значения `ErrBadRequest`, `ErrURITooLong`, `ErrHeaderTooLarge`, `ErrVersion`. Код ответа приходит вместе с ошибкой. Ошибка «липкая»: после неё `Feed` всегда возвращает её же — соединение надо закрыть, потому что непонятно, где кончается мусор.

**Мелочи:**
- `HeadLen()` — сколько байт занимает заголовок; тело (если есть) начинается после него. Нужно для keep-alive (шаг 5).
- `Reset()` — `*p = Parser{}`, обнуление структуры для следующего запроса.
- `VisitQuery` / `VisitCookies` — обход пар `name=value` через callback, без построения слайсов.

## 3. Безопасный путь: urlDecode и защита от ../

**Файлы:** `internal/http/path.go` (новый), `internal/http/path_test.go` (новый), `cmd/main.go`.

### Дыра

Путь к файлу собирался как `home + request.Path`. Запрос `GET /../cmd/main.go` отдавал **200 и исходник сервера** — проверено на живом сервере. Это path traversal, одна из первых вещей, которую ищет любой проверяющий.

### Решение: `CleanPath(dst, path []byte) ([]byte, error)`

1. **Сначала percent-decode, потом очистка.** Порядок важен: если сначала чистить, а потом декодировать, то `%2e%2e` (закодированное `..`) и `..%2f` (закодированный слэш) пройдут проверку и превратятся в `..` уже после неё.
2. **Очистка как `path.Clean`, но на месте:** `cleanInPlace` читает буфер индексом `r` и пишет в тот же буфер индексом `w`. Результат никогда не длиннее входа, поэтому `w` никогда не обгоняет `r` — можно писать в тот же массив. Без аллокаций.
3. **`..` не поднимается выше `/`:** `/../../etc/passwd` → `/etc/passwd`, который потом ищется **внутри** `www`. Так же ведёт себя `path.Clean`.
4. Двойные слэши схлопываются, `.` выбрасывается.
5. **Завершающий `/` сохраняется** — он означает «каталог» и нужен для поиска `index.html`.
6. Битый escape (`%zz`, `%2`) и NUL-байт (`%00`) → 400. NUL опасен тем, что в C-функциях обрезает строку.

**Мелочь:** `+` в пути **не** превращается в пробел. Это правило только для query в формате HTML-форм (`application/x-www-form-urlencoded`).

### Тесты

- `TestCleanPath` — 17 случаев, включая кириллицу `%D0%BA%D0%BE%D1%82` → `кот`.
- `TestCleanPathErrors`, `TestCleanPathAppends` (при ошибке `dst` не портится), `TestCleanPathZeroAllocs`, `BenchmarkCleanPath`.
- **`FuzzCleanPath`** проверяет главное свойство безопасности: в результате **нет сегментов `.`, `..` и пустых** — значит, склеенный с корнем путь не может выйти наружу. Плюс результат совпадает с `path.Clean` из стандартной библиотеки (эталон). 39 млн входов за 45 секунд.

### Живая проверка

```bash
printf 'GET /../cmd/main.go HTTP/1.1\r\n\r\n' | nc localhost 4321 | head -1
printf 'GET /%%2e%%2e/cmd/main.go HTTP/1.1\r\n\r\n' | nc localhost 4321 | head -1
```

`%%` — так в `printf` пишется символ `%`. До исправления: 200, после: 404.

## 4. Ответы: HEAD, 304, 405, дата, ETag

**Файлы:** `internal/http/time.go`, `conditional.go`, `conditional_test.go`, `responseBuilder_test.go` (новые); `responseBuilder.go`, `internal/file/fileReader.go`, `cmd/main.go`, `cmd/main_test.go`.

### Что исправлено и добавлено

1. **Баг в `Build()`:** пустая строка между заголовками и телом добавлялась только если тело есть. Ответ без тела (304, HEAD) выходил битым — клиент ждал продолжения заголовков. Теперь пустая строка всегда.
2. **Дата в формате HTTP.** `time.RFC1123` с зоной UTC печатает `UTC`, а HTTP требует буквально `GMT` (RFC 9110, 5.6.7). Константа `TimeFormat = "Mon, 02 Jan 2006 15:04:05 GMT"` и `FormatTime(t)` = `t.UTC().Format(TimeFormat)` — так же делает `net/http`. `ParseTime` принимает все три формата, которые RFC обязывает понимать: основной, устаревший RFC 850 и `asctime`.
3. **ETag** (`fileReader.go`, `getETag`) — время изменения и размер в hex, как в nginx: `"66f28e20-1a4"`. Меняется файл — меняется ETag, без чтения содержимого.
4. **Условные запросы** (`NotModified`, RFC 9110, 13.2.2):
   - если есть `If-None-Match` — решает только он, `If-Modified-Since` игнорируется;
   - ETag сравнивается **слабым** сравнением: `W/"x"` равно `"x"`; `*` совпадает с любым;
   - `If-Modified-Since`: время файла обрезается до секунды (`Truncate(time.Second)`), потому что в заголовке точность — секунда, а у файла — наносекунды. Без этого файл почти всегда казался бы «новее».
   - 304 без тела, но с `ETag` и `Last-Modified`.
5. **Методы:** GET и HEAD обслуживаются; OPTIONS → 204 с `Allow: GET, HEAD, OPTIONS`; остальные → 405 с тем же `Allow` (RFC 9110 требует `Allow` в 405).
6. **HEAD** — те же заголовки, включая `Content-Length` файла, но без тела. Файл при этом не читается.
7. **У ошибок** появились `Content-Length` и `Content-Type`; в теле 403 теперь «403», а не «404».
8. **`main.go` разбит на функции:** `serve` (выбор ответа), `fileReply`/`entryReply` (ответ с файлом), `newResponse`, `errorResponse`. Три почти одинаковых блока 200/403/404 ушли. Ошибка `net.Listen` больше не игнорируется.

### Сквозные тесты через `net.Pipe`

`cmd/main_test.go`, функция `roundTrip`: `net.Pipe()` создаёт пару соединённых в памяти `net.Conn`. Одну отдаём в `handleClient` (в горутине), в другую пишем запрос и читаем ответ. Настоящая сеть не нужна, тест проверяет весь путь: разбор → выбор файла → сборка ответа.

`TestServe` — 12 сценариев: индекс, файл, HEAD без тела, 404, **path traversal обычный и закодированный** (файл-приманка `outside.txt` лежит рядом с корнем), 400, 405, OPTIONS, 304 по дате, 505, 403 для нечитаемого файла (пропускается под root — root читает всё), `Date` оканчивается на `GMT`.

`TestNotModifiedByETag` — получаем ETag первым запросом, отправляем его в `If-None-Match` вторым, ждём 304.

## 5. Keep-alive и pipelining

**Файлы:** `internal/http/connection.go`, `connection_test.go` (новые); `cmd/main.go`, `cmd/main_test.go`.

### Правила (RFC 9112, 9.3)

- HTTP/1.1: соединение постоянное, **если нет** `Connection: close`.
- HTTP/1.0: соединение постоянное, **только если есть** `Connection: keep-alive`.
- `Connection` — список токенов через запятую, без учёта регистра (`Upgrade, CLOSE`). Разбирает `hasToken`.

### Как устроен цикл в `handleClient`

```
for served := 1; ; served++ {
    SetReadDeadline(now + 5s)
    parser.Reset()
    Feed(buff)               // байты следующего запроса могли уже прийти
    пока не done: Read -> Feed
    ответ
    keepAlive = KeepAlive() && !HasBody() && served < maxRequests
    Write
    если !keepAlive — выход
    сдвинуть остаток буфера в начало: buff = buff[:copy(buff, buff[HeadLen():])]
}
```

**Ключевые решения:**
1. **Pipelining.** Клиент может отправить несколько запросов подряд, не дожидаясь ответов. Тогда в буфере после `HeadLen()` уже лежит начало следующего запроса. Поэтому остаток не выбрасывается, а сдвигается в начало буфера, и новый запрос сначала разбирается из него, а читать из сокета нужно только если не хватило.
2. **Один дедлайн на чтение, 5 секунд.** Он ограничивает и простой keep-alive соединения, и медленную отправку заголовков. Второе — защита от атаки Slowloris: атакующий открывает тысячи соединений и шлёт заголовки по байту раз в несколько секунд, держа их открытыми. Дедлайны в Go — таймеры рантайма, а не системные вызовы, так что это дёшево.
3. **Дедлайн на запись, 30 секунд** — чтобы медленный клиент не держал горутину вечно.
4. **Не больше 1000 запросов на соединение** — как `keepalive_requests` в nginx: периодически соединения пересоздаются, нагрузка перераспределяется.
5. **После запроса с телом соединение закрывается.** Сервер тело не читает (методы с телом не поддерживаются). Если оставить соединение, непрочитанное тело будет разобрано как следующий запрос — это основа атак HTTP request smuggling. `HasBody()` смотрит на `Content-Length > 0` и `Transfer-Encoding`.
6. **После ошибки разбора — закрыть.** А вот 400 из-за битого пути (`/%zz`) соединение не закрывает: запрос прочитан целиком, граница известна.
7. **Таймаут и EOF** — нормальное завершение, в лог не пишется. `isTimeout` проверяет `net.Error.Timeout()`.

### Тесты

- `TestKeepAlive` (parser): 5 вариантов 1.0/1.1 и `Connection`. `TestHasBody`: 4 варианта.
- `TestKeepAlive` (cmd): **два запроса одной записью** (pipelining) → два ответа; третий с `Connection: close` → ответ и закрытие соединения (проверка через канал `finished` с таймаутом).
- `TestCloseAfter`: HTTP/1.0, запрос с телом, ошибка разбора, `Connection: close` в 1.0.
- `roundTrip` переделан: читает тело **по `Content-Length`**, а не до закрытия соединения — иначе с keep-alive тест висел бы 5 секунд.

### Живая проверка

```bash
curl -sv -o /dev/null -o /dev/null http://localhost:4321/ http://localhost:4321/index.html 2>&1 | grep -i "re-us"
# * Re-using existing connection! (#0) with host localhost
```

Таймаут простоя: `printf 'GET / HTTP/1.1\r\n\r\n' | nc localhost 4321` — соединение закрылось ровно через 5,00 с.

## 6. Производительность: методика и первый заход

**Файлы:** `cmd/main.go`, `internal/file/fileReader.go`, `internal/http/responseBuilder.go`, `cmd/main_test.go`.

### Методика замера

Главное правило: **сначала замер «до», потом оптимизация, потом замер «после»**. Иначе нельзя сказать, что помогло.

- Инструмент — `bombardier` (Go-аналог `wrk`): `go install github.com/codesenberg/bombardier@latest`. `ab` не подходит: он однопоточный и на 32 ядрах сам становится узким местом.
- Два файла: маленький 1 КБ и большой 1 МБ (разные узкие места: у маленького — обработка запроса, у большого — передача данных).
- Две нагрузки: 64 и 256 одновременных соединений, по 10 секунд, keep-alive.
- Сравнение с `net/http` (`http.FileServer`) и nginx 1.18 (`sendfile on; tcp_nopush on`, все ядра) на **тех же файлах и той же машине**.
- Скрипт вызывает `bombardier -c <N> -d 10s -l -p r -o json <url>` и печатает rps, p50, p99, пропускную способность и число не-2xx ответов. **Число не-2xx обязательно смотреть:** в первом прогоне `net/http` показывал высокие rps, но все ответы были 404 из-за неверного пути к файлам.

**Оговорки** (их надо писать рядом с цифрами): всё на одной машине по loopback, генератор нагрузки на тех же ядрах — абсолютные цифры завышены, честно сравнивать можно только серверы между собой.

### Что сделано

1. **`sendfile` для файлов больше 64 КБ.** Сначала пишутся заголовки, потом `io.Copy(conn, file)`. Для `*net.TCPConn` и `*os.File` Go внутри вызывает системный вызов `sendfile`: ядро копирует данные из page cache прямо в сокет, без копирования в память процесса. **Проверено через `strace`:** весь 1 МБ ушёл через `sendfile`, через `read` — только 14 КБ служебного.
2. **Маленькие файлы — одной записью** вместе с заголовками: меньше системных вызовов и TCP-пакетов.
3. **`sync.Pool` для буферов** чтения и записи: при тысячах коротких соединений не создаются новые буферы на каждое.
4. **Чтение прямо в буфер:** `slices.Grow(buff, 1024)` и `conn.Read(buff[len(buff):cap(buff)])` — без промежуточного `frame` и копирования.
5. **Заголовок `Date` раз в секунду.** Фоновая горутина обновляет строку, запросы читают её через `atomic.Pointer[string]` — без блокировок и без форматирования времени на каждый запрос.
6. **Буферизованный access log.** Раньше `fmt.Println` на каждый запрос = отдельный системный вызов `write`. Теперь `bufio.Writer` на 64 КБ, сброс раз в секунду.
7. **`Info()` больше не открывает файл.** Раньше для проверки прав файл открывался, из него читался байт, файл закрывался — три лишних вызова на запрос. Теперь проверкой служит само открытие перед отдачей: `os.IsPermission(err)` → 403. Добавлен метод `File.Open()`.
8. **`Response.AppendHead(dst)`** — заголовки дописываются в переданный буфер; убраны `[]byte(string)` на каждой строке, `strconv.AppendInt` вместо `Itoa`.
9. **Тест `TestLargeFile`** — файл больше 64 КБ, чтобы путь через `io.Copy` тоже был покрыт.

|---|---|---|---|

## 7. Профилирование и дожим: кеш, лог, TCP_CORK

**Файлы:** `cmd/cache.go`, `cmd/cork_linux.go`, `cmd/cork_other.go` (новые); `cmd/main.go`, `cmd/main_test.go`.

### Как снимался профиль, не трогая код

`perf` на машине не было, поэтому `runtime/pprof`. Чтобы не добавлять профилирование в репозиторий, использован **`go build -overlay`**: JSON-файл говорит компилятору «считай, что в `cmd/` есть ещё файл `zz_pprof.go`, вот его содержимое». Файл лежал во временном каталоге, в репозиторий не попал.

```json
{"Replace": {"/путь/к/проекту/cmd/zz_pprof.go": "/tmp/zz_pprof.go"}}
```

`zz_pprof.go` в `init()` запускает `pprof.StartCPUProfile`, через 12 секунд останавливает и пишет ещё профиль аллокаций. Сборка: `go build -overlay overlay.json -o server-prof ./cmd`. Анализ: `go tool pprof -top server-prof cpu.pprof`.

### Что показал профиль (маленький файл, c=256)

- **~50% CPU — системные вызовы.** Кроме неизбежных `read`/`write` сокета, на каждый запрос: `stat` (поиск файла), `open`, **`epoll_ctl`** (Go пытается зарегистрировать открытый файл в сетевом poller, для обычного файла это не удаётся, но вызов уже сделан), `read`, `close`.
- **~3% — `runtime.SetFinalizer`:** Go вешает финализатор на каждый `*os.File` (закрыть, если забыли).
- **~7% — access log:** форматирование времени на каждый запрос и конкуренция за общий мьютекс.
- Парсер — около 1%. Он больше не узкое место.

### Что сделано

1. **Кеш маленьких файлов** (`cmd/cache.go`):
   - файлы до 64 КБ, суммарно не больше 64 МБ;
   - ключ — очищенный путь запроса, значение — содержимое, ETag, время изменения и **заранее собранные заголовки** (`Last-Modified`, `ETag`, `Content-Type`, `Content-Length`);
   - `sync.Map` — структура, оптимизированная для «много читают, редко пишут»: чтение без блокировок;
   - **запись доверяется 1 секунду** (`cacheValid`), потом следующий запрос идёт на диск и обновляет её. Изменение файла становится видно не позже чем через секунду. Аналог `open_file_cache_valid` в nginx, но nginx кеширует только дескрипторы, а здесь — содержимое;
   - лимит памяти: счётчик `atomic.Int64`, при превышении запись удаляется `CompareAndDelete` (удалить, только если там всё ещё именно эта запись — защита от гонки с параллельным обновлением);
   - для 304 из готовых заголовков берутся только `Last-Modified` и `ETag` (функция `validators`, поэтому они стоят первыми).
2. **Лог:** время в формате лога тоже обновляется раз в секунду (`logTime`), адрес клиента вычисляется один раз на соединение, строка собирается в буфер соединения **до** взятия мьютекса — под мьютексом остаётся только копирование в `bufio.Writer`.
3. **`TCP_CORK` для больших файлов** (`cork_linux.go`) — аналог `tcp_nopush` в nginx. Пока сокет «закупорен», ядро не отправляет неполные пакеты: заголовки ответа (~200 байт) и начало файла уходят вместе, полными пакетами, а не отдельным крошечным пакетом с заголовками. Опция ставится через `SyscallConn().Control` → `setsockopt`. Только Linux: остальные ОС получают пустую функцию через build-тег `//go:build !linux` в `cork_other.go`. Сборка под macOS проверена: `GOOS=darwin go vet ./cmd`.
4. **Изоляция тестов:** кеш пережил смену `home` между тестами и отдал файл из предыдущего теста. Добавлен `setHome(root)`, который меняет корень и очищает кеш.
5. **`TestCacheRefresh`:** файл меняется, через `cacheValid + 100 мс` должно прийти новое содержимое.

### A/B-замер TCP_CORK

Один замер ничего не доказывает — разброс между прогонами бывает 5–10%. Поэтому версии без и с `TCP_CORK` запускались поочерёдно дважды: 43,8 / 48,3 / 43,3 / 48,4 тыс. rps. Прирост +11% стабилен, изменение оставлено.

## 8. Компромиссы и что не сделано

| Что | Почему так |
|---|---|
| Кеш показывает изменения с задержкой до 1 с | цена скорости; то же у nginx `open_file_cache_valid`. Для статики нормально |

## 10. Вопросы, которые зададут на собеседовании

**Почему конечный автомат, а не `strings.Split` по строкам?**
Автомат разбирает байты по мере прихода из сокета и продолжает с того же места. Split требует сначала собрать весь запрос и найти его конец — то есть разобрать дважды. Плюс автомат проверяет каждый байт по грамматике RFC, а Split пропустит мусор.

**Как получился ноль аллокаций?**
Результат — смещения в буфере вызывающего, методы возвращают срезы, а не копии. Заголовки — фиксированный массив в структуре. Сравнение без учёта регистра без конвертации в `string`. Это закреплено тестом `AllocsPerRun == 0`.

**Что будет, если запрос придёт по одному байту?**
Автомат вернёт «нужно ещё» и продолжит с того же состояния. Есть тест, который подаёт запрос побайтово, и fuzz-тест, который режет вход в случайном месте.

**Как защищён путь?**
Сначала декодирование, потом очистка `..` — иначе `%2e%2e` пройдёт. `..` не поднимается выше корня. Fuzz проверяет, что в результате нет сегментов `..`, и сверяет с `path.Clean`.

**Что такое sendfile и почему это быстрее?**
Системный вызов, который копирует данные из файла в сокет внутри ядра, без копирования в память процесса и обратно. В Go он вызывается автоматически через `io.Copy` из `*os.File` в `*net.TCPConn`. Проверял через `strace`.

**Зачем TCP_CORK?**
Чтобы маленький пакет с заголовками не уходил отдельно от данных файла. Мерил A/B дважды: +11% на файлах 1 МБ.

**Как устроен keep-alive и что такое pipelining?**
Правила RFC 9112, 9.3. Остаток буфера после текущего запроса — начало следующего, поэтому он не выбрасывается. Соединение закрывается после запроса с телом, иначе непрочитанное тело разберётся как запрос (request smuggling).

**Как ты мерил и почему веришь цифрам?**
Замер до и после, два размера файла, две нагрузки, сравнение с net/http и nginx на одной машине, проверка доли не-2xx ответов, повторные прогоны для A/B. Оговорка: loopback и генератор на той же машине.

**Как нашёл, что оптимизировать?**
Профиль CPU через pprof: половина времени в системных вызовах, конкретно `stat`/`open`/`epoll_ctl`/`close` на каждый запрос, 3% на финализаторы файлов, 7% на лог. Отсюда кеш и переделка лога.

**Честный ответ про инструменты:** «Делал вместе с AI-ассистентом, но каждое решение проверял тестами и замерами и могу объяснить». В 2026 году это ожидаемо и ценится — если действительно можешь объяснить. Для этого — раздел 11.

## 12. Конфиг, виртуальные хосты и JSON-лог

**Файлы:** `cmd/server/config.go`, `cmd/server/log.go`, `pkg/config/base.go`, `cmd/server/cache.go`, тесты `config_test.go`, `log_test.go`.

### Конфиг
- `pkg/config`: поиск файла (`Find`) отделён от чтения (`Load(file, &anyStruct)`), `NewBase` работает поверх них. Так один пакет годится для любого формата конфига.
- Файл: флаг `-config path`, без флага — поиск `config.yml`, `config/config.yml`, `/etc/goHttpServer/...`.
- Каждый элемент `servers` — виртуальный хост (как `server {}` в nginx). Значения по умолчанию: `listen: localhost:4321`, `host: default`, `indexes: [index.html, index.htm]`, `logFormat: json`.
- **Проверка при старте, а не при первом запросе:** `home` должен быть каталогом, `logFormat` — `json` или `text`, пара `listen`+`host` не повторяется. Ошибка конфига — сразу выход с понятным сообщением (`servers[1]: home "..." is not a directory`), а не 404 на проде.

### Общие настройки
- `serverName`, `readTimeout`, `writeTimeout`, `maxRequests` — на верхнем уровне, а не у хоста: они действуют на соединение, а хост известен только после чтения заголовков. Не указаны — берутся значения по умолчанию (`defaultSettings`).
- `allowedMethods` остался в коде: он описывает, что сервер **умеет**, а не как настроен. `POST` в конфиге не научил бы сервер его обрабатывать.
- **Ловушка с длительностями:** `yaml` читает `readTimeout: 5` как 5 **наносекунд**, проверка `> 0` проходит, и сервер рвёт все соединения. Поэтому тип `Duration` со своим `UnmarshalYAML` принимает только строку с единицами (`5s`, `500ms`), голое число — ошибка.
- `serverName` попадает в заголовок `Server`, поэтому CR/LF и прочие непечатные символы запрещены: иначе конфиг мог бы вписать в ответ лишние заголовки.

### Виртуальные хосты
- Хосты группируются по `listen`: на каждый адрес один `net.Listen`, на нём несколько сайтов.
- Выбор по заголовку `Host` (`pickHost`): порт отрезается (`a.test:8080` → `a.test`, IPv6 `[::1]:80` → `[::1]`), сравнение без учёта регистра. Не нашли — хост `default`, нет и его — первый в списке.
- **У каждого хоста свой кеш.** Раньше ключом был путь `/index.html`, и два сайта отдавали бы файлы друг друга. Лимит памяти (64 МБ) общий.

### Логи
- **Системные события** (старт, поиск конфига, ошибки чтения) — `log/slog` с `JSONHandler` в **stderr**. Скорость тут не важна, важна структура.
- **Access-лог** — в **stdout**, формат из `logFormat` хоста. Разделение потоков — стандарт для контейнеров: сборщик логов разбирает их по-разному.
- JSON-строка собирается **руками**, а не через `encoding/json`: без рефлексии и без аллокаций (`TestAccessLogAllocs` проверяет 0 аллокаций). Замер: ~460–530 тыс. rps при 64 соединениях, как и раньше.
- **Экранирование:** `Host` и URI присылает клиент. Без экранирования запрос с `Host: x"}\n{"status":200` сломал бы строку или подделал лишнюю запись в логе (log injection). Кавычки и `\` экранируются, управляющие символы и байты ≥ 0x80 превращаются в `\u00XX`.

### Вопросы для самопроверки
1. Зачем проверять конфиг при старте, если ошибка всё равно вылезет при первом запросе?
2. Почему у каждого виртуального хоста свой кеш? Что сломалось бы с общим?
3. Как из `Host: [::1]:8080` получить имя хоста и почему нельзя просто резать по первому `:`?
4. Почему системные логи — в stderr, а access-лог — в stdout?
5. Что такое log injection и как её здесь предотвращает `appendJSONString`?
6. Почему access-лог не пишется через `slog` или `encoding/json`? Когда это было бы нормально?
7. Почему `readTimeout: 5` опасен и как тип `Duration` это предотвращает?
8. Почему таймауты — общие настройки, а не настройки виртуального хоста?

### Упражнения
1. Верни 400 на запрос HTTP/1.1 без `Host` и добавь тест.
2. Добавь в access-лог размер ответа (`bytes`) и время обработки (`duration_us`). Проверь, что аллокаций по-прежнему 0.
3. Сделай перечитывание конфига по `SIGHUP` без остановки сервера. Подсказка: `atomic.Pointer` на таблицу хостов, как сделано с `dateHeader`.
